# 0.4.0 — DSH `0.1.7` line

Release notes for `dsh-edit-approval@0.4.0`.

---

## Compatibility — read this first

| | |
| --- | --- |
| **Supported DSH range** | **the `0.1.7` line only** |
| Verified against | `@deepseek-ai/*@0.1.7-rc.2` — the line's `latest`, and the version this release pins in `devDependencies` |
| Declared as | `peerDependencies`: one `^0.1.7-rc.1` tuple per harness package; `dsh.engines.dsh = ">=0.1.7-rc.1"` |
| Earlier lines | **refused** — DSH skips the bundle at startup with a peer diagnostic |
| Node.js | `^22.19.0 \|\| >=24.0.0` |

`^0.1.7-rc.1` covers both `0.1.7-rc.1` and `0.1.7-rc.2`: a same-tuple prerelease
roll needs no peer change. The floor stays at `rc.1` because both were verified,
and `node scripts/check-dsh-version.mjs` reports `covered: 2/27 … ceiling
0.1.7-rc.2`.

**This release does not work on DSH 0.1.6 or earlier, and is not meant to.** DSH
0.1.7 replaced the settings-namespace registry this plugin used for both its
features with one live `Config` per profile entry, and removed the browser
`dsh-client-runtime` package and the `settingsScope` service. There is no 1:1
successor for the old model, so tracking an older line as well would mean
maintaining two settings models, two client write paths and two session-read
shapes. The plugin tracks one line at a time.

> Note on the two semver rule sets, because they are easy to confuse: **npm**
> only matches a prerelease candidate when the range carries a comparator on the
> *same* `[major, minor, patch]` tuple — so npm would want a new `||` term per
> tuple. **DSH's startup gate** evaluates with `includePrerelease`, so a single
> `^0.1.x-pre` term already spans the whole `0.1` line. A union therefore does not
> narrow anything at the gate; it only overstates what was verified. The full
> reasoning is in [`docs/compat/0.1.7-audit.md`](../compat/0.1.7-audit.md) §1.

## Breaking changes

The `edit-approval` and `bash-approval` settings namespaces are gone. Both
features now live on one profile entry — the `dsh-edit-approval` row the bundle
patch inserts — and every key is renamed:

| Old namespace | Old key | New key | Where |
| --- | --- | --- | --- |
| `edit-approval` | `enabled` | `editEnabled` | Plugins panel |
| `edit-approval` | `tools` | `editTools` | profile file |
| `edit-approval` | `minDiffLines` | `editMinDiffLines` | profile file |
| `edit-approval` | `includeCreate` | `editIncludeCreate` | profile file |
| `edit-approval` | `includeDelete` | `editIncludeDelete` | profile file |
| `bash-approval` | `enabled` | `bashEnabled` | Plugins panel |
| `bash-approval` | `tools` | `bashTools` | profile file |
| `bash-approval` | `allow` | `bashAllow` | profile file |

`alwaysAllow` (removed in `f182d92`) stays gone.

**Your settings do not migrate.** DSH imports a legacy `settings.yaml` section
into the entry of the **same name**, and neither old name is a profile entry id —
so those sections are logged and left in `settings.yaml.imported`. Restate what
you had in the profile patch, or set it once on the new panel:

```yaml
# profile's cordis.patch.yml
- id: dsh-edit-approval
  name: dsh-edit-approval
  config:
    bashEnabled: true
```

## What changed

- **A configuration panel on the bundle's page** in the sidebar's **Plugins**
  panel, replacing the two Settings → General rows. It uses the harness's own
  staged form (`SettingsForm` + `Switch`), so a change is previewed and written
  on **Save**. Only the two master switches appear there; the other six keys stay
  in the profile file, exactly as before.
- **Live switches.** The two switches are the entry's only live fields: they take
  effect immediately, with no restart. A switch written back to its default is
  *cleared* rather than pinned, so the profile patch keeps only what you actually
  changed and a later default change still reaches you. The `/approval-*`
  commands apply the same rule, so the panel and the commands cannot disagree.
- **`str_replace_editor` is no longer intercepted by default** — it stopped being
  a default DSH tool in 0.1.3. Its guard branches are still shipped and tested;
  add the name to `editTools` to gate it.
- **No runtime dependencies.** `diff` is now bundled into the host artifact.
- **Removed dead paths**: the settings-namespace indirection, the `canonicalPath`
  cwd probe (0.1.7's fs tools resolve `session.header.cwd` verbatim, so
  canonicalizing previewed a different file identity than the tool mutated), and
  the client's dual-channel chat reader — the browser half reads no session state
  at all now, which is why it needs only `slots`, `locale` and `configForms`.
- **Bilingual, shorter package description**, plus `locale/{en,zh}.json` so the
  bundle card's title and one-liner follow the active language. No icon is
  shipped.

The approval panel itself is unchanged: the red/green line diff, the collapse
button and focus restore are the same code, because the panel's structural
anchors survived the line change untouched.

## Verification

Machine-checked, against the real `0.1.7-rc.2` packages:

- `npm run typecheck` — clean on both compilation surfaces, against the real types.
- `npm test` — **140 tests** across 10 suites.
- `npm run verify:host` — **33 checks** driving the **built** host artifact on a
  real cordis Context, with its settings double anchored to the real
  `SettingsForms.prototype` in both directions.
- `scripts/build.mjs` smoke checks — the client bundle may inline **no**
  `node_modules` input, and neither bundle may reference a package the target
  line removed.
- The published tarball was downloaded back and its contents confirmed (41 files:
  both bundles, declarations, `locale/*.json`, `docs/`, `cordis.patch.yml`,
  `LICENSE`).

## Known boundaries

- **Command copy is English-only** (the two `/approval-*` descriptions and every
  result line). The harness translates no third-party command copy and no command
  output, and carrying a dictionary for four sentences is ongoing maintenance this
  plugin deliberately does not take on. The panel and card copy *do* follow the
  active language.
- **The config panel needs a loopback page.** On a non-loopback page the settings
  transport degrades to process-local, writes return `false`, and the form renders
  read-only.
- **The approval panel DOM is an unsanctioned coupling.** `data-approval-key`,
  `data-approval-scroll` and the headline's position are not documented as a
  contract; they have now survived one line change unchanged, which is why the
  panel features remain a DOM enhancement.
- **`displayReason` is available but unused.** `0.1.7-rc.2` added
  `PreToolDecision.ask.displayReason` — a localized-prompt map the client resolves
  through its own locale runtime. That makes the approval **headline** cheaply
  localizable (unlike command copy). Adopting it changes user-visible copy, so it
  is left as a follow-up rather than folded into a compatibility release.

## Upgrade

```sh
dsh plugin --profile web add dsh-edit-approval     # or update in the Plugins panel
# restart `dsh web` (`--profile web`)
# then restate any previous bash-approval preference (see above)
```

Already on DSH `0.1.7-rc.2`? No runtime change is required on your side beyond the
settings rename.

# 0.4.0 — 适配 DSH `0.1.7` 线

`dsh-edit-approval@0.4.0` 发布说明。

---

## 兼容范围 —— 请先读这一节

| | |
| --- | --- |
| **支持的 DSH 范围** | **仅 `0.1.7` 这一条线** |
| 验证目标 | `@deepseek-ai/*@0.1.7-rc.2` —— 该线的 `latest`，也是本次 `devDependencies` 钉住的版本 |
| 声明方式 | `peerDependencies` 每个 harness 包一个 `^0.1.7-rc.1` 元组；`dsh.engines.dsh = ">=0.1.7-rc.1"` |
| 更早的线 | **会被拒绝** —— DSH 在启动时跳过该 bundle 并给出 peer 诊断 |
| Node.js | `^22.19.0 \|\| >=24.0.0` |

`^0.1.7-rc.1` 同时覆盖 `0.1.7-rc.1` 与 `0.1.7-rc.2`：同一元组的预发布滚动无需改动 peer。floor 保留在 `rc.1`，因为两者都验证过；`node scripts/check-dsh-version.mjs` 报告 `covered: 2/27 … ceiling 0.1.7-rc.2`。

**本版本不支持 DSH 0.1.6 及更早，也不打算支持。** DSH 0.1.7 把本插件两扇门共用的设置命名空间注册表换成了"每个 profile 条目一个 live `Config`"，同时删除了浏览器侧 `dsh-client-runtime` 包与 `settingsScope` 服务。旧模型没有 1:1 后继，因此同时兼容更早的线意味着维护两套设置模型、两条客户端写路径与两种会话读取形状。本插件一次只追一条线。

> 关于两套 semver 规则的一个提醒，这里很容易混淆：**npm** 只在 range 里存在同 `[major, minor, patch]` 元组的比较器时才允许预发布候选命中——所以 npm 会希望每个元组追加一个 `||` term。而 **DSH 的启动闸**用 `includePrerelease` 求值，因此单个 `^0.1.x-pre` 已覆盖整条 `0.1` 线。所以并集并不能在闸上收窄任何东西，只会**夸大验证范围**。完整推理见 [`docs/compat/0.1.7-audit.md`](../compat/0.1.7-audit.md) §1。

## 破坏性变更

`edit-approval` 与 `bash-approval` 两个设置命名空间已不存在。两扇门现在共用**一个 profile 条目**——bundle patch 插入的 `dsh-edit-approval` 行——且所有键都改了名：

| 旧命名空间 | 旧键 | 新键 | 位置 |
| --- | --- | --- | --- |
| `edit-approval` | `enabled` | `editEnabled` | 「插件」面板 |
| `edit-approval` | `tools` | `editTools` | profile 文件 |
| `edit-approval` | `minDiffLines` | `editMinDiffLines` | profile 文件 |
| `edit-approval` | `includeCreate` | `editIncludeCreate` | profile 文件 |
| `edit-approval` | `includeDelete` | `editIncludeDelete` | profile 文件 |
| `bash-approval` | `enabled` | `bashEnabled` | 「插件」面板 |
| `bash-approval` | `tools` | `bashTools` | profile 文件 |
| `bash-approval` | `allow` | `bashAllow` | profile 文件 |

`alwaysAllow`（已在 `f182d92` 移除）保持移除。

**旧设置不会自动迁移。** DSH 会把旧 `settings.yaml` 的 section 导入**同名**条目，而这两个旧名字都不是 profile 条目 id——因此那些 section 只会被记日志并留在 `settings.yaml.imported` 里。请把你原有的设置写进 profile patch，或在新面板上拨一次：

```yaml
# profile 的 cordis.patch.yml
- id: dsh-edit-approval
  name: dsh-edit-approval
  config:
    bashEnabled: true
```

## 本次变更

- **配置面板移到侧栏「插件」面板里本插件的页面上**，取代原来的两个 设置 → 通用 开关行。它使用 harness 自带的暂存表单（`SettingsForm` + `Switch`），改动先预览、按 **保存** 才写入。面板上只有两个总开关；其余六个键仍在 profile 文件里，与之前一致。
- **开关是 live 的。** 两个开关是该条目唯一的 live 字段：改动立即生效，无需重启。开关被拨回默认值时是**清除**而非固化，因此 profile patch 只保留你真正改过的东西，日后的默认值变更仍能送达你。`/approval-*` 命令遵循同一规则，所以面板与命令不可能不一致。
- **`str_replace_editor` 默认不再被拦截**——它自 DSH 0.1.3 起不再是默认工具。针对它的 guard 分支仍然随包发布并有单测；把该名字加进 `editTools` 即可启用。
- **无运行时依赖。** `diff` 已打进 host 产物。
- **删除了死路径**：设置命名空间的间接层、`canonicalPath` cwd 探测（0.1.7 的 fs 工具按 `session.header.cwd` 原文解析，做规范化会让预览指向与实际改写不同的文件身份），以及客户端的双通道 chat 读取器——浏览器半边现在完全不读会话状态，因此只需要 `slots`、`locale`、`configForms`。
- **双语且更精简的包描述**，并新增 `locale/{en,zh}.json`，使 bundle 卡片的标题与一句话简介跟随当前语言。不带图标。

审批面板本身未变：红绿行级 diff、折叠按钮与焦点恢复是同一份代码，因为面板的结构锚点在这次换线中逐字未变。

## 验证

针对真实的 `0.1.7-rc.2` 包做了机器校验：

- `npm run typecheck` —— 两套编译面在真实类型上零错误。
- `npm test` —— 10 个套件、**140 项测试**。
- `npm run verify:host` —— **33 项检查**，在真实 cordis Context 上驱动**已构建**的 host 产物，且其 settings 替身双向锚定到真实的 `SettingsForms.prototype`。
- `scripts/build.mjs` 冒烟检查 —— 客户端产物**不得**内联任何 `node_modules` 输入；两个产物都不得引用目标线已删除的包。
- 把**已发布**的 tarball 下载回来核对了内容（41 个文件：两个产物、类型声明、`locale/*.json`、`docs/`、`cordis.patch.yml`、`LICENSE`）。

## 已知边界

- **命令文案仅英文**（两个 `/approval-*` 的描述与所有结果行）。harness 不翻译任何第三方命令文案与输出，而为四句话维护一套字典是持续的维护负担，本插件有意不背。面板与卡片的文案**确实**跟随当前语言。
- **配置面板需要 loopback 页面。** 非 loopback 页面上设置传输会降级为进程内，写入返回 `false`，表单呈现为只读。
- **审批面板 DOM 是非契约耦合。** `data-approval-key`、`data-approval-scroll` 与 headline 的位置未被 harness 记为契约；它们已安然穿过一次换线，这也是面板增强仍以 DOM 方式存在的原因。
- **`displayReason` 可用但未采用。** `0.1.7-rc.2` 给 `PreToolDecision.ask` 加了 `displayReason`——一份由客户端用自身 locale 运行时解析的本地化提示映射。这让审批 **headline** 可以便宜地本地化（不像命令文案）。采用它会改变用户可见文案，因此留作后续，而不是塞进一个以兼容为目标的版本。
