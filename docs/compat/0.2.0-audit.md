# Compatibility audit — DSH 0.2.0 line

> **Method: the tests are the audit.** The probes in `tests/config.spec.ts`,
> `tests/integration.spec.ts`, `tests/package-layout.spec.ts` and
> `scripts/verify-host.mjs` drive this plugin's real execution paths against the
> **real** `@deepseek-ai/*` packages — not against hand-written doubles that
> agree with whatever the plugin happens to call. `scripts/build.mjs` carries the
> artifact-side half of the same discipline.
>
> **Line history.** This plugin tracked the `0.1.7` line from 0.4.0 and rolled
> to `0.2.0` at 0.5.0, through `0.2.2-rc.2`. Sections 1, 2 and 4–7 are the record
> of the `0.1.7` rewrite — what broke, why it was silent, and the settings model
> that line introduced — and every one of those seams is byte-identical on
> `0.2.2-rc.2`, so that record still describes the code the plugin runs today.
> §3.1–§3.3 are the roll-by-roll deltas.
>
> Verified against: `@deepseek-ai/*@0.2.2-rc.2`, the version `devDependencies` pin
> exactly. The peers declare `^0.2.0-rc.1` and `engines.dsh` repeats that same
> bounded range — it must stay bounded, because from `0.2.2` the gate reads it
> alone and ignores the peers (§3.3). The window is
> `[0.2.0-rc.1, 0.3.0-0)`: `0.2.x` is admitted, while `0.1.7-rc.2` and
> `0.3.0-rc.1` are refused — all measured by calling the harness's own
> `evaluatePluginCompatibility`, not inferred from the range.
> Source references are to the upstream monorepo
> [github.com/deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)
> at tag `dsh-v0.2.2-rc.2`, or to the published packages under
> `@deepseek-ai/dsh@0.2.2-rc.2/node_modules`.

## 1. Version alignment: one line at a time

`peerDependencies` declare **one** `^X.Y.Z-pre` tuple per harness package, and
`engines.dsh` carries the same bounded range, under the standard npm `engines`
field, which is where the upstream manifest type (`DshEnginesManifest`) names it.
That field is not decorative: from `0.2.2` the admission gate lets an own
`engines.dsh` decide **alone** and ignores every peer, so this copy must keep its
`^` — see §3.3. As of `0.2.0-rc.1` the older `dsh.engines.dsh` location has no
reader left upstream. A second `||` term would re-declare a DSH line this plugin
does not track.

Two different semver rule sets are in play, and confusing them is easy:

| Rule set | `^0.1.5-rc.1` vs `0.1.7-rc.1` |
| --- | --- |
| npm's default prerelease matching | **false** — a prerelease candidate only matches when the range has a comparator on the *same* `[major, minor, patch]` tuple, so a new tuple needs a new `||` term |
| DSH's startup admission gate (`semver.satisfies(rt, range, { includePrerelease: true })`) | **true** — one caret term on any `0.1.x-pre` already covers the whole `0.1` line |

So the previous multi-tuple union (`^0.1.0-rc.6 || ^0.1.1-rc.2 || ^0.1.2-rc.1 ||
^0.1.5-rc.1`) was **admitted** on 0.1.7 and then failed at the API level — and no
peer spelling within `0.1.x` could have stopped it, because the gate cannot
distinguish "verified on 0.1.5" from "verified on 0.1.7". Narrowing to one tuple
is therefore a statement of what was actually verified (and it does make the gate
refuse *older* lines, which is the truthful outcome), not a way to make the gate
catch this class of break.

`node scripts/check-dsh-version.mjs` guards the declaration itself: identical
tuple sequence across every harness peer, engine floor in sync with the oldest
floor, and a report when the registry publishes above the declared window.

## 2. What actually broke (and why nobody saw it)

Three independent failures were in play. **Any one of them was sufficient to
make the plugin do nothing**, and all three were silent.

### 2.1 The host half mounted and then threw

`src/index.ts` called `scope.settings.register(...)` inside its
`ctx.inject(['settings','commands','fs'], …)` callback. DSH 0.1.7 removed
`SettingsForms.register` entirely. cordis catches an inject callback's throw,
logs it, and disposes the child fiber — so `apply()` itself did not throw.

Reproduced by mounting the built artifact against the real
`SettingsForms.prototype`:

```
real SettingsForms.prototype: constructor, importLegacyDocument, configure,
  invalidate, writable, documentPath, prepareDocument, describe, update,
  replace, mutate, write, schema
has .register? undefined
apply() threw synchronously: no
errors surfaced through ctx.logger: 1
  - TypeError: scope.settings.register is not a function
tools/pre-execute baseline reached: true; decision={"kind":"allow"}   ← no listener
```

The commands and the `tools/pre-execute` listener were registered *after* the
throw, so **neither ever mounted**: every edit ran unapproved, with one log line
as the only trace.

### 2.2 The client half never ran

`inject` named `settingsScope`, which exists in **0 of the 277 packages** of
0.1.7. cordis leaves a fiber with an unsatisfied inject inactive — no log, no
throw:

```
apply ran with an unsatisfiable inject present: false
apply ran when every inject is satisfiable:        true
```

So the browser half contributed nothing at all: no diff rendering, no collapse
button, no focus restore, no settings rows, not even the injected `<style>`.

### 2.3 The startup gate admitted it anyway

Verified by calling the harness's own exported
`evaluatePluginCompatibility(manifest, {}, '0.1.7-rc.1')` with this package's
real manifest: `ADMITTED (no incompatible peers)`. See §1 for why the previous
union satisfied it.

### 2.4 Why the test suite stayed green

`scripts/verify-host.mjs` hand-rolled a `settings` service implementing **only**
`register` — the single method 0.1.7 had just deleted — while the plugin under
test called `settings.register`. Suite and plugin agreed with each other and
with nothing real. (`devDependencies` were also pinned to 0.1.1-rc.2, so
`tsc` type-checked the plugin against the old surface too.)

The fix is structural, not a new assertion: the double is now anchored to the
**real** `SettingsForms.prototype` in both directions, so it can neither invent a
member the service lacks nor silently cover for a removal. Removing the anchor
demonstrably fails the suite:

```
FAIL the settings double implements only members the real service has — register
```

### 3.2 The `0.1.7-rc.2 → 0.2.0-rc.1` crossing

**Manifest only. No source change.** Every file this plugin reads was verified
byte-identical between the two tags:

| Seam file | `rc.2 → 0.2.0-rc.1` |
| --- | --- |
| `packages/core/tools/src/index.ts` | unchanged |
| `packages/settings/settings/src/{index,schema}.ts` | unchanged |
| `packages/client/ui-approval/src/client/ApprovalPanel.tsx` and `contract/slots.ts` | unchanged |
| `packages/client/ui-plugin-manager/src/client/slot-contract.ts` | unchanged |
| `packages/client/ui-settings/src/client/config-form{,-types}.ts` | unchanged |
| `packages/client/ui-primitives/src/settings-form/{form-model.ts,SettingsForm.tsx}` and `Switch.tsx` | unchanged |
| `packages/client/web/src/platform.ts` (`PLATFORM_MODULES`) | unchanged |
| `packages/interaction/commands/src/index.ts` | unchanged |
| `packages/client/locale/src/locale-settings.ts` | unchanged |

The near-misses are all inert for this plugin: `ui-primitives/src/Switch.module.css`
(+4 lines, styling), `plugin-artwork.tsx` (the fallback card artwork) and one
added export in `ui-primitives/src/index.ts`. `cordis` (4.0.4) and `schemastery`
(3.18.4) are unchanged, which is why those two peers keep their own independent
ranges. The declaration is the whole adaptation: replaced peer tuples, the exact
`devDependencies` pin, the changed version, and the floor moved to
`engines.dsh`.

**A crossing is refused unless the peers move, and that is a different mechanism
from a same-tuple rc roll.** A caret range's desugared upper bound carries a
`-0`:

```
^0.1.7-rc.1  →  >=0.1.7-rc.1 <0.2.0-0
^0.2.0-rc.1  →  >=0.2.0-rc.1 <0.3.0-0
```

Because `0.2.0-0 < 0.2.0-rc.1` (numeric identifiers sort below alphanumeric
ones), that upper bound excludes the **next minor's own prereleases** — under the
gate's `includePrerelease` as well as npm's default rules:

| Runtime | `^0.1.7-rc.1` | `^0.2.0-rc.1` |
| --- | --- | --- |
| `0.1.7-rc.2` | admitted | refused |
| `0.2.0-rc.1` | **refused** | admitted |
| `0.3.0-rc.1` | refused | refused |

So a minor crossing is a hard boundary at the gate while an rc roll inside a
tuple is invisible to it. That asymmetry is why a cursor at a new line
*replaces* the peer tuple instead of widening it: a union would admit both lines,
and the gate would stop distinguishing what was actually verified — which is
exactly how the `0.1.7` break went unnoticed (§2). `scripts/check-dsh-version.mjs`
fails closed when the registry publishes above the declared ceiling.

### 3.3 The `0.2.0-rc.1 → 0.2.2-rc.2` crossing

Two upstream changes. Neither shows up in the packages this plugin imports at
build time — both were found by running the plugin, which is the point.

**1. The approval panel gained a wrapper (a real break).** `ui-approval` grew a
shared `ApprovalCard` / `ApprovalWarning`, and the headline moved out of the
scroll body's first element child into a `.heading` row:

```
body[data-approval-scroll]
├─ [subject]
├─ .heading            ← new; display: flex; align-items: center; flex-wrap: wrap
│   ├─ .headline       ← the reason text (our diff)
│   └─ [ApprovalWarning]
├─ [description]
└─ [.command]
```

Every selector this plugin had was positional, so all of them — the two CSS
rules and the diff rebuild — started targeting that flex wrapper. The rebuild
then appended its per-line rows as flex children, laying them out side by side
and wrapping: the panel's line structure broke. Both data attributes
(`data-approval-key`, `data-approval-scroll`) were unchanged, which is why the
failure was confined to the line layout.

Fixed by anchoring on content instead: the headline is the element owning the
first non-empty text node in the body — the node that carries the diff's `\n`
breaks — and the plugin's own `dsh-ea-diff-*` row classes keep that lookup valid
after a rebuild. See `src/client/headline.ts`. The two CSS rules needed no
change in substance: `white-space`, `font-family`, `font-size` and `line-height`
are all inherited, so pointing them at the body seat reaches the headline
wherever it sits.

**2. The admission gate changed who it asks (a silent ceiling loss).** In
`0.2.2`, `unmetRequirements` reads an own `engines.dsh` and *ignores every
peer*:

```js
if (Object.hasOwn(engines, "dsh")) {
  return satisfies(runtimeVersion, engines.dsh) ? {} : { "engines.dsh": engines.dsh }
}
// ...otherwise: every @deepseek-ai/dsh or @deepseek-ai/dsh-* peer must match
```

This plugin had moved its declared floor to `engines.dsh` in `0.2.0` (§3.2) with
only a LOWER bound, `>=0.2.0-rc.1`. Under the old gate that was harmless because
the peers still decided. Under the new one it removed the ceiling entirely.
Measured against the 0.2.2-rc.2 gate:

| `engines.dsh` | 0.2.2-rc.2 | 0.3.0-rc.1 | 1.0.0 |
| --- | --- | --- | --- |
| `>=0.2.0-rc.1` (what shipped) | admitted | **admitted** | **admitted** |
| `^0.2.0-rc.1` (fixed) | admitted | refused | refused |
| *absent*, peers `^0.2.0-rc.1` | admitted | refused | refused |

So `engines.dsh` now carries the same bounded range as the peers, and
`scripts/check-dsh-version.mjs` fails closed if it does not. That script also had
to stop classifying releases by tuple: it now measures them against the same
`[floor, next-minor-0)` window the gate applies, so the two cannot disagree —
before, it reported `0.2.2-rc.2` as *above* the window while the gate admitted it.

**3. The independently versioned dependencies moved too.** `cordis` went
`4.0.4 → 4.1.0` and `schemastery` `3.18.4 → 3.19.0`. Pinning the old pair left a
nested `schemastery@3.19.0` under every harness package, and declaration emit
failed with:

```
error TS2883: The inferred type of 'Config' cannot be named without a reference
to 'Schema' from '@deepseek-ai/dsh-tools/node_modules/@deepseek-ai/schemastery'
```

Two copies of one schema library mean two `Schema` types, and the inferred type of
the plugin's `Config` referred to the one it could not name portably. Bumping both
peers and devDependencies to the shipped versions deduped it to a single copy.
`typecheck` had passed throughout — only the declaration-emit step caught this,
which is why `npm run build` is part of the gate rather than a separate step
someone remembers to run.

## 4. The settings model on this line

- **One entry.** The `Config` schema lives on the `dsh-edit-approval` profile row
  — the row the bundle patch inserts, whose `id`, `name` and npm package name are
  the same string. The settings service keys entries by `entry.options.id` for
  direct children of the root include, and every composed row is one, so that id
  is exactly what a write addresses.
- **Two live fields, six ordinary ones.** Only `editEnabled` and `bashEnabled`
  are `.volatile()`. A volatile field is the only kind a form shows and the only
  kind a write may address, so marking one volatile *is* the decision to expose
  it. The rest are read as plain values when the entry loads; making them
  volatile would add live-update machinery they do not need.
- **Clear, don't pin.** A switch written back to its schema default is UNSET, not
  stored. Pinning a copy of today's default would silently opt the user out of a
  later default change, and it would put a value in the profile patch that the
  user never chose. The `/approval-*` commands and the config card apply the same
  rule, so the two write paths cannot leave the document in different shapes.
- **The page opts out of generation.** `configure({ auto: false }, ctx.fiber)` is
  registered as an effect inside a `ctx.inject(['settings'])` child, which is the
  documented gesture for a plugin that ships its own page. The owner MUST be the
  plugin's own fiber: the service looks the policy up by `entry.fiber`, so the
  inject child's default owner would store it where nothing reads it. Inert today
  (no shipped client builds pages from `autoGenerate`), pinned in `verify-host`.
- **The config page.** Registered into `plugins.bundle.config` with
  `key: 'dsh-edit-approval'`. The shell renders that section only when a
  contribution registered a `key` equal to the package name the Host reports
  (`ledger.bundles.has(pkg.name)`), so a wrong key makes the card silently
  absent. The shell passes **no** `form` prop for this slot — unlike
  `plugins.item` / `plugins.row.config` — so the card obtains the form itself
  through `ctx.configForms.get(entryId)`, which is structurally the
  `SettingsFormScope` the model wants (no cast).

## 5. Known behavior boundaries

- **Legacy settings do NOT migrate.** DSH's settings service imports each
  `settings.yaml` section into the entry of the **same name**. The old sections
  were `edit-approval` and `bash-approval`; the new entry is `dsh-edit-approval`.
  Both old sections are therefore logged and left in `settings.yaml.imported`. A
  user who had turned command approval on must restate `bashEnabled: true` in the
  profile patch or flip the switch once. This is a documented consequence, not a
  silent one — but it is silent *in the UI*, which is why it is called out in both
  READMEs and in the release note.
- **Ordinary fields are not live.** Changing `editTools` / `editMinDiffLines` /
  `editIncludeCreate` / `editIncludeDelete` / `bashTools` / `bashAllow` requires
  the entry to reload. Pinned in `verify-host` ("an ordinary field keeps its
  mount-time value").
- **The config page requires a loopback page.** `ctx.configForms` persistence is
  `host` only when `ctx.remote.$host.isLoopback`; otherwise it degrades to
  `memory` and every write returns `false`, so the card renders read-only. Not
  exercised here.
- **The approval panel DOM is an unsanctioned coupling — and it did move.** The
  two data attributes survived the `0.1.7 → 0.2.0` roll, but `0.2.2` wrapped the
  headline in a `.heading` flex row, and every selector here was positional
  (`[data-approval-scroll] > div:first-child`). The predicted failure was
  "the diff stops being colored"; what actually happened was worse — the rebuild
  injected its rows into the flex wrapper, so they laid out side by side and the
  panel's line structure broke. The lookup is now content-anchored (§3.3), which
  is what makes a further wrapper harmless rather than fatal.
- **The panel is a composer takeover.** `ui-approval` registers into
  `conversation.composer` (a chain, `priority: 1`, `overlay: true`), so the panel
  renders in the composer seat rather than inline in the stream. Selectors are
  unaffected; the visual position moved.
- **Save from the card is transactional; the commands are immediate.** The card
  stages edits and writes them on Save; `/approval-edit on|off` writes at once.
  Both end up in the same document with the same clear-on-default rule.
- **Command copy is English-only, by decision.** The two `/approval-*`
  descriptors and every result line are literal English strings in the host half,
  while the client half's card and panel copy do follow the user's language. That
  split is deliberate rather than an oversight: localizing the host copy means
  reading the user's preference through the settings service on every registration
  and every render, which is ongoing maintenance for four sentences. The
  constraint that forces it is in §7 — the harness translates no third-party
  command copy, so a plugin that wants it must carry it.

## 6. Uncovered boundaries (need a live browser)

Settled by source and unit probes, but not yet observed in a running page:

1. The rendered panel tree — that nothing interposes between `card` and `strip`,
   and that `[data-approval-scroll] > div:first-child` really is the headline
   (class names are build-generated hashes).
2. That the plugin's headline rewrite survives the panel's `setAnswered(true)`
   re-render (React should not touch a string child's replacement nodes).
3. That resolving an approval **unmounts** the panel rather than hiding it —
   `refocus` observes a removal.
4. That the host's edit-approval reason still matches `isDiffReason`'s
   `/\n\s*\d+\| [+-]/` shape.
5. That the card appears on the bundle's page in the sidebar's Plugins panel, and that its form reports
   `writable` with `mode: 'host'` on a loopback page.
6. That `dsh-client-ui-settings-general` (which declares `settings.general.item`)
   is composed — no longer needed by this plugin, but its absence would have made
   the old rows wait forever.

## 7. Upstream observations

- The **`.check()` API** the settings cookbook recommends for cross-field Config
  validation does not exist in the vendored Schemastery (3.18.4). Full-Config
  validation before persistence happens through `resolveConfig` inside
  `ConfigEditor.edit`.
- The **cookbook says a custom plugin page receives `form.state` / `form.mutate`**
  from the Plugins page owner. That holds for `plugins.item` and
  `plugins.row.config`, but **not** for `plugins.bundle.config`, whose only owner
  prop is `{ view: 'page' }`.
- The **`SettingsForms` README's `autoGenerate` rule** ("a plugin that ships its
  own page registers `configure({ auto: false }, ctx.fiber)`") is followed by the
  first-party plugins that both own a namespace and ship UI (ui-chat, ui-theme,
  locale, ui-settings-general, …), but not by the first-party *companion page*
  packages — which is consistent, since a companion does not own the namespace it
  renders. It is inert today because no shipped client consumes the flag.
- The settings subsystem doc states consumers read the session policy through
  `ctx.approval.effectivePolicy(session)`; that method is **private** on
  `ApprovalService`. `overrideOf(session) ?? config.policy` remains the public
  route and is what this plugin uses.
- **Host command copy is not localizable by a third party.** The client
  translates a command's descriptor only for the first-party allowlist
  `HOST_FACES` (goal, plan, feedback, compact, permission, export); every other
  command falls through to `{ description: c.description }` — the host's raw
  string, verbatim. Command *output* is never localized for anyone: the
  execution notice renders `outcome.text` as-is. A plugin that wants either must
  carry its own dictionary and read the preference itself, which on this line
  means `ctx.settings.describe({ redactSecrets: true })` against the `locale`
  entry's `preference` field — the locale host half registers no settings
  section, only `configure({ auto: false })`. This plugin does not do that (see
  §5).
- **The APPROVAL PROMPT, unlike command copy, became localizable in `0.1.7-rc.2`.**
  `PreToolDecision.ask` gained
  `displayReason?: { readonly en: string; readonly [locale: string]: string }`,
  which `ToolRuntime` forwards to the approval request
  (`packages/core/tools/src/index.ts`, `packages/interaction/user-approval/src/types.ts`).
  The panel prefers it and resolves the map through the client's own locale
  runtime — `ctx.locale.resolveText` — falling back to `reason` when absent
  (`packages/client/ui-approval/src/client/ApprovalPanel.tsx`). No
  `settings.describe` read and no registration-time/render-time split is needed,
  which is what made command-copy localization expensive.
  This plugin sends `reason` only, so the panel renders the English headline; the
  client-side diff rebuild is keyed on the `NN| +`/`-` markers rather than on the
  header text, so a localized header would not disturb it. Adopting it is a
  user-visible copy decision left as a follow-up, not a compatibility gap.
